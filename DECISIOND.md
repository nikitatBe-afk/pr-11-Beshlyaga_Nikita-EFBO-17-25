# DECISIONS.md — Индивидуальный вариант 4

## 1. Номер варианта

Вариант: **4**.

## 2. Часть А. Обязательная дата рождения

**Правило:** расширение R2 и валидации карточки клиента новым обязательным полем `birthDate`.

**Что было:** строка CSV состояла из трёх полей `inn;name;email`. Типы `ClientDraft` и `Client` содержали только эти значения.

**Что стало:** строка состоит из четырёх полей `inn;name;email;birthDate`. Дата рождения обязательна и записывается в карточку клиента. `ClientCsvParser.parse` проверяет количество полей, а `ClientValidator.validate` проверяет календарную дату в строгом формате `ГГГГ-ММ-ДД` и отклоняет будущую дату.

**Почему:** проверка на этапе импорта предотвращает сохранение пустой, некорректной или невозможной даты. Отдельный валидатор сохраняет прежнее разделение обязанностей: парсер отвечает за структуру CSV, валидатор — за смысл полей.

**R8:** дубликат ИНН отклоняется с записью в `ImportResult.errors`; импорт следующих строк продолжается.

## 3. Часть Б. Новый метод

**Класс:** `ClientValidator`.

**Метод:** `addAgeCategory`.

**Сигнатура:** `public String addAgeCategory(String birthDate)`.

**Назначение:** вычисляет полный возраст на текущую системную дату через `LocalDate` и `Period`. Возвращает «до 18», «18–65» или «старше 65». Ровно 18 и ровно 65 лет входят в среднюю категорию. Неверная или будущая дата вызывает `IllegalArgumentException`, как и при валидации карточки.

**Код метода:**

```java
public String addAgeCategory(String birthDate) {
    int age = Period.between(
            parseBirthDate(birthDate), LocalDate.now()
    ).getYears();
    if (age < 18) return "до 18";
    if (age <= 65) return "18–65";
    return "старше 65";
}
```

Общий приватный метод `parseBirthDate` проверяет шаблон `yyyy-MM-dd`, разбирает календарную дату и запрещает будущее. Поэтому анализ возраста и проверка при импорте не расходятся в трактовке даты.

## 4. Ответы на контрольные вопросы

**Вопрос 1. Какая проверка защищает программу от наиболее вероятной ошибки входных данных и где она расположена?**

Проверка даты рождения в `ClientValidator.validate(ClientDraft)` защищает новый обязательный столбец варианта 4. При ручном заполнении CSV особенно легко перепутать порядок года, месяца и дня, оставить поле пустым или указать несуществующее число вроде `2023-02-29`. Метод `parseBirthDate` сначала проверяет точный формат `ГГГГ-ММ-ДД`, затем вызывает `LocalDate.parse` и исключает будущую дату. Если значение некорректно, валидатор возвращает сообщение об ошибке, а `ClientImporter.importFile` записывает его с физическим номером строки. Такая строка не сохраняется, однако следующие строки файла продолжают обрабатываться. Это важно и для метода возрастной категории: он может вычислять возраст только по действительной дате.

**Вопрос 2. Какой метод или класс содержит ключевое бизнес-правило и почему оно размещено там?**

Правило варианта 4 находится в `ClientValidator`: метод `validate(ClientDraft)` требует корректную дату рождения, а `addAgeCategory(String)` определяет возрастную группу на текущую дату. Такое размещение оправдано тем, что проверка календарной даты и вычисление возраста являются правилами данных клиента. `ClientCsvParser` отвечает только за четыре поля и не должен решать, существует ли указанное число в календаре. `ClientImporter` отвечает за чтение файла, сохранение корректной карточки и локальную регистрацию ошибок, поэтому ему достаточно вызвать валидатор. Общий приватный `parseBirthDate` предотвращает расхождение между проверкой при импорте и анализом возраста. Для изменения границ категорий не придётся переписывать код чтения CSV или репозитория.

**Вопрос 3. Как Activity-диаграмма отражает конкретный участок кода?**

На Activity-диаграмме блок «Разобрать 4 поля CSV» соответствует вызову `ClientCsvParser.parse(line, lineNumber)` внутри `ClientImporter.importFile`. Следующий блок «Проверить ИНН, имя, email и дату рождения» соответствует вызову `ClientValidator.validate(draft)`. Если в дате ошибка, валидатор возвращает сообщение, импортёр создаёт `IllegalArgumentException`, а локальный `catch` добавляет `ImportError` с номером строки. Стрелка от блока ошибки к чтению следующей строки отражает продолжение цикла и правило R6. После успешной проверки программа отдельно ищет дубликат ИНН и либо регистрирует ошибку, либо сохраняет `Client` с полем `birthDate`. Таким образом, схема показывает реальные ветви кода, включая изменение индивидуального варианта.

**Вопрос 4. Какое изменение требования затронет минимальное количество классов и почему?**

Например, если границу последней возрастной категории изменить с 65 на 60 лет, основную бизнес-логику нужно исправить только в `ClientValidator.addAgeCategory`: сравнение `age <= 65` заменяется на `age <= 60`. `ClientCsvParser` по-прежнему разбирает четыре поля, `ClientImporter` сохраняет карточки, а `ClientRepository` ищет их по ИНН. Ни формат CSV, ни тип `Client` при этом не меняются. Дополнительно надо обновить соответствующие проверки `SelfCheck`, чтобы ожидаемые ответы совпадали с новым правилом. Это пример локализации требования: границы возрастных групп сосредоточены в одном методе, а остальная архитектура не зависит от конкретных чисел.

## 5. Фрагмент кода для анализа

**Проблемный фрагмент:**

```java
try {
    for (String line : lines) {
        importLine(line);
    }
} catch (Exception e) {
    return;
}
```

Общий `catch` расположен снаружи цикла. Поэтому первая некорректная строка прерывает обработку всего файла: оставшиеся, в том числе правильные, записи не импортируются. Кроме того, `return` скрывает причину ошибки и не создаёт запись с физическим номером строки, как требует R5.

**Исправленный подход:**

```java
int lineNumber = 1;
for (String line : lines) {
    lineNumber++;
    try {
        importLine(line);
    } catch (IllegalArgumentException e) {
        result.addError(new ImportError(lineNumber, e.getMessage()));
    }
}
```

Локальная обработка ошибки позволяет продолжить цикл после плохой записи (R6) и сохранить причину с номером строки (R5). Ошибка открытия файла остаётся `IOException` и завершает импорт целиком (R7).
